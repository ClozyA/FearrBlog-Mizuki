# 旧站功能迁移到新版上游设计

## 目标

以当前 `upstream/master` 为代码主体，恢复备份分支
`origin/backup/publish-before-content-split-20260722` 中用户实际使用的全部站点功能、配置、数据和静态资源，同时保留文章分仓、每周上游同步 Action 与 EdgeOne 的 `publish` 部署流程。

## 基线与边界

- 新版基线为当前 `publish`，其代码历史包含最新 `upstream/master`。
- 旧站事实来源为备份提交 `490fde1`，该提交保持只读，不做改写。
- 文章正文继续由 `ClozyA/FearrBlog-Content` 同步，旧站内置示例文章不恢复。
- 不直接复制旧版组件树覆盖新版；新版已有等价功能时使用新版实现。
- 不在本次迁移中加入旧站从未启用的新功能，也不进行无关重构。

## 迁移策略

### 1. 配置语义迁移

旧站以 `src/config.ts` 集中配置功能，新版上游使用 `src/config/*.ts` 模块化配置。迁移以配置含义为准，而不是按文件内容覆盖：

- 站点身份、域名、语言、主题色和日期格式；
- 导航栏、个人资料、侧栏布局、公告和页脚；
- 横幅、全屏壁纸、轮播和页面视觉效果；
- 音乐播放器、评论、分享、目录、相关文章和随机文章；
- 看板娘、樱花、统计和其他旧站已配置的可选功能。

对每个旧配置项建立“旧位置 → 新位置 → 迁移值”的清单。新版不存在的字段不得静默丢弃：先确认是否由新版自动行为替代，再决定是否需要兼容代码。

### 2. 数据与静态资源迁移

恢复旧站用户数据及其引用的资源，包括头像、横幅、壁纸、音乐、友链、项目、设备、日记、相册和其他页面数据。只迁移旧站实际引用的资源，避免恢复上游演示内容或无引用的大文件。

所有资源路径按新版配置和组件接口校验；如果新版推荐的文件格式或路径发生变化，保留视觉内容并更新引用，不恢复失效引用。

### 3. 组件兼容迁移

先建立功能存在性矩阵：

- 新版已有且可配置：只迁移配置和数据；
- 新版已有但接口变化：编写最小适配；
- 新版已移除且旧站实际启用：将旧行为移植到新版结构；
- 旧站未启用或仅为开发示例：不迁移。

组件迁移不得回退新版上游的路由、布局、依赖版本或安全修复。

## 自动同步保护

每周同步仍以正常 Git 合并把 `upstream/master` 合入维护分支。功能恢复提交必须位于 `publish` 历史中，使后续合并保留本地配置；工作流不得从上游重新创建或重置 `publish`。

同步后的验证顺序保持为：内容同步、功能清单测试、现有测试、Astro 检查、生产构建。任一步失败都不更新 `master` 或 `publish`，并沿用 GitHub Issue 失败通知。

## 测试与验收

### 自动化测试

- 新增功能清单测试，检查重要功能配置、导航入口和必要资源存在。
- 保留现有文章分仓及每周同步工作流测试。
- 运行 `pnpm test`、`pnpm check` 和 `pnpm run build`。
- 验证工作流不重置或强制覆盖 `publish`。

### 页面验收

对旧站主要能力逐项核验：首页身份和横幅、导航、左右侧栏、音乐、评论、目录、分享、推荐、友链、项目、设备、日记、相册、时间线、技能页、主题与壁纸设置，以及移动端入口。

构建产物中必须保留独立内容仓库的三篇历史文章，不恢复上游示例文章。

## 发布与回退

完成本地验证后，将恢复提交正常推送到 `publish`，由 EdgeOne 自动部署。部署后检查首页、主要功能页和三篇文章。若线上验收失败，立即将 `publish` 回退到本次发布前的远端提交；旧站备份分支 `490fde1` 始终保留，不删除。

## 成功标准

- 页面以新版上游实现为主体；
- 旧站实际使用的功能、个性化配置、数据和视觉资源均已恢复；
- 三篇历史文章继续来自独立内容仓库；
- 每周同步不会再次以重建分支的方式丢失本地功能；
- 自动化检查、生产构建和线上关键页面验证全部通过。
